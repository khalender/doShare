1. Encrypting a key with another key

A key is 32 bytes. Bytes can be encrypted like any data. Encrypting a key with another key is called wrapping, and the result is a wrapped key: 32 bytes of key plus nonce and tag, stored in the open next to the data.

data key (DEK) encrypts the data answer → ciphertext key-encryption key encrypts the data key DEK → wrapped DEK to read: unwrap the DEK with the KEK, then decrypt the data with the DEK

This pattern is called envelope encryption. Cloud providers use it for everything they store: AWS KMS, Google Cloud KMS and Apple's iCloud Keychain all hand out data keys wrapped under a key the customer or device controls.

This is the answer to your question from before. A teacher "having access" means a wrapped copy of the data key exists that the teacher's key can unwrap. No copy, no access, whatever the server says. And the server holds no key that unwraps any copy.

2. Why not encrypt the data straight with everyone's key?

  • Sharing. To let 3 people read a 2 MB page of ink, wrap the 32-byte data key 3 times (240 bytes) instead of storing 3 encrypted copies of the ink (6 MB).
  • Adding a reader later. Wrap the data key once more. The ink is not touched.
  • Changing a key higher up. If a class key changes, rewrap the 100 enrolment keys under the new one (8 KB of work). The pupils' work stays as it is.
  • Different reach for different people. Each layer of the tree is a different circle of readers, as the next section shows.

3. The doSlim school tree

school key ─ wraps ─▶ class key Maths 7B ─ wraps ─▶ enrolment key Ayşe·Maths ─ encrypts ─▶ Ayşe's maths work └ wraps ─▶ class key Chem 7B ─ wraps ─▶ enrolment key Ayşe·Chem ─ encrypts ─▶ Ayşe's chemistry work Ayşe's key pair ─ sealed copy (lesson 2) ─▶ Ayşe·Maths and Ayşe·Chem who holds what: each admin the school key (wrapped for the admin's account key pair) Ms Kaya the Maths 7B class key (wrapped for her account key pair) Mr Arslan the Chem 7B class key Ayşe her own key pair (from the card)

Reading is walking down the tree from a key you hold. The admin goes school → class → enrolment → data. Ms Kaya starts one level lower, so she reaches everything under Maths 7B and nothing under Chem 7B. Ayşe enters from the side, through the sealed copies made for her, and only her own enrolment keys have one.

Two kinds of wrapping are mixed on purpose. Class and school keys are symmetric, so a teacher's iPad wraps with lesson 1's cipher. A pupil's copy is a sealed box for her public key (lesson 2), because the teacher's iPad must be able to give her a key without ever holding her private key.

4. Granting and revoking

Granting is adding a wrapped copy. Mr Arslan adds Ayşe to Chemistry: his iPad makes the Ayşe·Chem key, wraps it under the Chem class key, checks Ayşe's public key against the signature chain (lesson 2), and seals a copy for it.

Revoking is harder, and the honest part of every encryption design: you cannot make someone forget what they already read. When Ms Kaya leaves:

  1. The server deletes her wrapped copy of the class key. Her device can no longer get it from the server.
  2. Her device may still have the old class key. So the admin's device makes a new class key, and new work goes under it.
  3. The existing enrolment keys are rewrapped under the new class key. Old work stays readable for the new teacher, without re-encrypting the work itself.

Making a new key so a removed member cannot read what comes next is called key rotation. Everything Ms Kaya downloaded before she left, she keeps. No system can take that back.

5. How a teacher's account opens (T17, already built)

A teacher's private key is itself wrapped, once per unlock method, and the wrapped copies sit on the server. A new iPad downloads them and opens whichever it can:

MethodThe wrapping key comes from
PasswordArgon2id(password, salt), lesson 1. The server gets a separate login proof, never this key.
PasskeyThe WebAuthn PRF extension: the passkey (iCloud Keychain, Google, Windows Hello) returns a secret per site that only it can produce.
Another deviceAn already signed-in device seals the private key for the new device's throwaway public key, shown as a QR.
Recovery words24 words = 256 random bits, written on paper.

So the whole doSlim tree hangs from four or so wrapped copies per adult. Forget the password, and any other method still opens the same private key.

6. The pupil card

  1. Ms Kaya's iPad makes 32 random bytes: Ayşe's seed (lesson 2, section 9). From it, Ayşe's key pair.
  2. It signs Ayşe's public key with Ms Kaya's key, seals Ayşe's enrolment keys for it, and uploads the public key, the signature and the sealed copies. The seed stays on Ms Kaya's iPad only long enough to print.
  3. The QR holds https://…/card/TOKEN#SEED. A browser sends /card/TOKEN to the server to sign in, but never the part after #, the fragment. The page's own code reads the fragment and rebuilds the key pair on the iPad.
  4. The iPad stores the private key as a non-extractable WebCrypto key in IndexedDB: the page can use it to decrypt but no script can read its bytes out. On a shared iPad it sits behind Ayşe's PIN.

[!] Limits to know. The page's code reads the fragment, so code the server sends could still steal it (section 9). A non-extractable key cannot be copied off the device, but it can be used by anyone who can run code on that device while it is unlocked. And libsodium's 25519 keys are not WebCrypto keys everywhere yet, so the build may need to keep the private key wrapped under a non-extractable AES key instead. A detail for the task, not a change to the design.

7. Lost keys: rewrap from above

Every key in the tree has a copy wrapped under the key above it. That makes recovery a rewrap, never a decrypt-everything:

LostWho fixes itWhat their device does
Ayşe's cardMs Kaya (for Maths), Mr Arslan (for Chem), or an admin (for all)New seed and key pair, new card; unwrap each Ayşe enrolment key with the class key, seal it for the new public key; the server drops the old sealed copies and the old card's token.
Ms Kaya's every unlock methodAn adminMs Kaya makes a new account key pair; the admin's device unwraps the Maths 7B class key through the school key and wraps it for her new public key.
Every admin's keyNobodyThe top of the tree has nothing above it. Hence 2 or more admins, and a printed school recovery sheet in the safe.

8. Two locks on the answer key

The worksheet's answer key must reach Ayşe's iPad (it grades on the device, D22), but she must not read it before hand-in. T17 locks it twice: once with the class's assignment key, then again with a release key the server holds. At hand-in the server records the hand-in and gives out the release key. Ayşe alone has one lock open, the server alone has the other: neither can read it alone. Both together only after the hand-in is on record.

9. What the tree does not protect

  • [-] The code. The web app comes from doSlim's server. A dishonest release could send keys home. Mitigations: published build hashes (D22), a native app with store-signed builds (T22).
  • [-] Metadata. The server sees which ids are in which class, how many rows, their sizes and times. Names and content are encrypted; the shape is not.
  • [-] The device. An unlocked iPad with malware, or a pupil reading over a shoulder, is outside any encryption.
  • [-] The past. A removed member keeps what they downloaded (section 4).
  • [x] The school reads everything. Not a hole: the school is the controller of pupils' data under GDPR. State it in the agreement.

10. Why not a web3 design

HD wallets (BIP32) derive child keys from a parent key: school seed → teacher keys → pupil keys. That gives "the parent can open the child" for free, which looks like our tree. Two problems. A teacher who leaves still holds a key that derives every pupil key under it, forever, and you cannot rotate one key without moving it to a new place in the tree. In our design each key is random and only wrapped under its parent, so rotating is a rewrap.

A blockchain solves agreement on an order of events between parties who do not trust a common server. doSlim has one server and no such need, and a public chain would publish metadata about minors permanently.

What we do take from web3: keys made and kept on the device, a seed as a portable private key (the card), and signatures checked against a known root.
