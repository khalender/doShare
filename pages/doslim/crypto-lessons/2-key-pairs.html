1. The sharing problem

Lesson 1 left a gap. Ms Kaya's iPad has a 32-byte key and Ayşe's iPad needs it. They are in different places, and the only thing between them is doSlim's server, which must not see the key. Sending it in plain would hand it to the server. Encrypting it needs another shared key, which has the same problem. Public-key cryptography breaks the loop.

2. Key pairs: a public half and a private half

A key pair is two linked keys made together on a device. The private key never leaves that device (or leaves only encrypted). The public key can be shown to anyone, the server included. The math links them so that what one half does, only the other half can check or undo, and the private key cannot be worked out from the public one.

Think of the public key as an open padlock you hand out by the hundreds. Anyone can snap it shut on a box. Only you have the key that opens it.

The 25519 family is built on one elliptic curve (Curve25519). Small keys, fast, and designed so the easy way to use it is the safe way. In general use one pair for encryption and another for signing.

3. Agreeing on a secret in public (Diffie-Hellman)

In 1976 Diffie and Hellman showed that two parties can each combine their own private key with the other's public key and arrive at the same secret, while someone watching sees only the two public keys and cannot compute it.

The paint picture: both start with the same public yellow. Ayşe adds her secret red and sends the orange mix. Ms Kaya adds her secret blue and sends the green mix. Each adds their own secret colour to what they received. Both end with yellow + red + blue, the same brown. The watcher has orange and green and cannot unmix them.
shared = X25519(my private key, your public key) Ayşe: X25519(ayse_private, kaya_public) ─┐ Kaya: X25519(kaya_private, ayse_public) ─┴─ same 32 bytes server: has ayse_public and kaya_public → cannot get there

The shared 32 bytes then go through a KDF and become a symmetric key for lesson 1's ciphers. Public-key math is slow and handles small values; it is only used to set up a symmetric key, which then does the real work. This is called hybrid encryption, and every real system works this way, including TLS.

4. Encrypting to someone's public key: the sealed box

Often the sender has no key pair of their own in the conversation, or should not need one. libsodium's crypto_box_seal handles that:

  1. Make a throwaway (ephemeral) key pair for this one message.
  2. X25519 of the throwaway private key and the recipient's public key gives a shared secret.
  3. Encrypt the message with it (XSalsa20-Poly1305), nonce derived from the two public keys.
  4. Send the throwaway public key (32 bytes) + ciphertext + tag (16 bytes). Delete the throwaway private key.

Only the recipient's private key can redo step 2. Even the sender cannot open the box afterwards. The overhead is 48 bytes, so sealing a 32-byte key gives 80 bytes, the number from the earlier page. In doSlim, a sealed box is how Ms Kaya's iPad gives Ayşe the Ayşe·Maths key: encrypt the key, not the data, for her public key.

Sealed boxes are anonymous: the recipient learns nothing about who sealed it. If the sender matters, add a signature (section 5) or use crypto_box, which uses the sender's real key pair.

5. Signatures: proof of who made it

A signature runs the pair the other way round. The private key signs a message and produces 64 bytes (Ed25519). Anyone with the public key can verify that exactly this message was signed by that private key. Change one bit of the message, or use another public key, and verification fails.

signature = sign(teacher_private, message) 64 bytes verify(teacher_public, message, signature) → true / false
  • [x] A signature hides nothing. The message stays readable; signing and encrypting are separate jobs.
  • [x] It proves origin and integrity: who, and that nothing changed.
  • [x] Lesson 1's tag also proves nothing changed, but everyone with the shared key can make a valid tag. Only the private key holder can make a signature.
  • [-] A signature does not prove when, and an old signed message can be replayed. Put a date or version inside what you sign.

6. The swap attack: why public keys need checking

Public keys solve sharing, but open a new hole. Ms Kaya's iPad asks the server: "What is Ayşe's public key?" A dishonest server answers with a key pair it made itself. The iPad seals Ayşe's key for the server's key. The server opens it, reads it, and even seals it again for the real Ayşe so nobody notices. This is the man-in-the-middle attack, and it is the real reason for your CA idea.

Kaya's iPad → "Ayşe's public key?" → server server → returns EVIL_public (it keeps EVIL_private) Kaya's iPad → seal(EVIL_public, ayse_maths_key) → server opens it encryption worked perfectly; it encrypted for the wrong person

Encryption cannot catch this, because the encryption worked. Only a check that the public key really belongs to Ayşe catches it.

7. Fingerprints: checking a key by eye

A fingerprint is a short hash of a public key, shown as words or digits. Two people compare it through a channel the server does not control: in person, on paper, by phone. Signal's "safety numbers" and WhatsApp's security code QR are this. It works, but nobody will compare 500 pupils' fingerprints by hand. Signatures scale it.

8. Chains of trust and CAs

Instead of checking every key by eye, check one key by eye and let it vouch for others with signatures. That trusted key is the root; the one who holds it is a certificate authority (CA). A certificate is a public key plus a name, signed by the key above it.

The web: root CA (built into your iPad) → signs → Let's Encrypt R11 → signs → doslim.example's TLS key doSlim: school signing key (fingerprint on paper) → signs → Ms Kaya's key → signs → Ayşe's key Mr Arslan's iPad, before sealing anything for Ayşe: check Ayşe's key is signed by a teacher key, that teacher key is signed by the school key, the school key matches the fingerprint the school entered once → only then seal
  • The root must arrive outside the system it protects. Browsers ship root keys with the operating system; a school gets its fingerprint on the welcome sheet or from the admin's own device.
  • The web uses X.509 certificates, a large format with expiry dates and revocation lists. A three-level doSlim chain only needs raw Ed25519 signatures over "this key belongs to this pupil id in this school".
  • Revocation: when a card is lost, the chain must also say "this key no longer counts". Simplest form: the school keeps a signed list of current pupil keys, and devices use the newest.
  • Back to your question: the CA decides which keys to trust. It does not decrypt anything, and it does not need to see any data.

9. Seeds: a key pair from 32 bytes

A key pair can be made from a 32-byte seed in a fixed way: the same seed always gives the same pair (libsodium crypto_sign_seed_keypair, crypto_box_seed_keypair). So the seed is the private key in a portable form.

  • Crypto wallets write the seed as 24 words (BIP39): 2,048 possible words is 11 bits each, 24 words is 264 bits, of which 256 are the seed and 8 a checksum.
  • doSlim's pupil card carries the seed as a QR instead of words. Scan the card, rebuild the key pair. Lesson 3 covers where it sits in the URL and why.
  • Whoever holds the seed holds the key. A seed must be random (lesson 1), never derived from a name or a PIN.
