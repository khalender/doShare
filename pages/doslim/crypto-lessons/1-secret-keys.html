1. What encryption does

Encryption turns readable data (the plaintext) into bytes that look random (the ciphertext), using a key. Decryption turns the ciphertext back, and only works with the right key.

plaintext: "Ayşe: 7 × 8 = 56" key: 3f 9a 1c … (32 random bytes) ciphertext: e1 07 9b 4c 22 f0 … (looks like noise)

The point that confused us in the last message: the ciphertext is what gets stored. There is no readable copy behind it that a rule protects. Whoever gets the ciphertext without the key gets noise.

Kerckhoffs's principle. The method (the algorithm) is public. Only the key is secret. AES and ChaCha20 are published and studied by thousands of people; their safety comes from the key, not from hiding how they work. Never trust a system whose safety depends on its method staying secret.

2. A key is just random bytes

A modern key is 32 bytes, which is 256 bits, picked at random. Nothing more. To guess it, an attacker tries keys one by one. With 256 bits there are 2256 keys, about 1077. If every computer on Earth tried a billion billion keys per second, the sun would burn out long before they got through a tiny fraction.

So a key is never broken by guessing. Keys are lost in other ways: they leak, they are stored next to the data, they are made from something guessable (a PIN, a birthday), or they come from a bad random source.

Random source: in a browser, crypto.getRandomValues() asks the operating system for real randomness. Math.random() is predictable and must never make a key.

3. One key, both ways: symmetric encryption

When the same key encrypts and decrypts, the cipher is symmetric. The two you will meet:

XSalsa20-Poly130532 bytes24 bytes16 byteslibsodium's crypto_secretbox, used by doSlim (T17)

A correction to my last message: I said doSlim's crypto_secretbox is XChaCha20-Poly1305. It is XSalsa20-Poly1305. Same design family, same sizes, same safety for our use.

How a stream cipher like Salsa20 or ChaCha20 works, in one line: the key and nonce produce a long stream of random-looking bytes (the keystream), and the cipher XORs it with the plaintext. XOR is "flip the bit where the keystream has a 1". Doing it again with the same keystream flips the bits back.

plaintext 01000001 ("A") keystream 10110110 XOR → 11110111 ciphertext keystream 10110110 XOR → 01000001 back to "A"

4. The nonce: a number used once

If the same key always made the same keystream, two messages encrypted with it would share it. XOR the two ciphertexts and the keystream cancels out, leaving plaintext XOR plaintext, which is often easy to read. The nonce fixes this: a fresh value per message, mixed in with the key, so every message gets its own keystream.

  • [x] The nonce is not secret. It is stored next to the ciphertext.
  • [x] It must never repeat for the same key. Reuse is the classic way real systems break.
  • [x] With a 24-byte nonce you can just pick it at random; the chance of a repeat is negligible. With AES-GCM's 12 bytes, random nonces are safe only up to about 4 billion messages per key.
  • [x] Same plaintext, same key, new nonce: completely different ciphertext. That also hides when two pupils wrote the same answer.

5. The tag: noticing a change

Encryption alone hides data but does not stop someone from changing it. With XOR, flipping a bit in the ciphertext flips the same bit in the plaintext, so an attacker could turn a mark of 5 into a 7 without reading anything. Authenticated encryption adds a 16-byte tag (Poly1305 or GCM's GHASH) computed from the key and the ciphertext. Decryption checks the tag first. One changed bit anywhere and decryption refuses, with no partial output.

So "decrypts fine" means two things at once: the right key was used, and nobody changed a single byte since it was encrypted.

6. Hashes are not encryption

A hash such as SHA-256 turns any input into 32 bytes. It has no key and no way back. The same input always gives the same hash; a one-letter change gives a completely different one.

SHA-256("doslim") = 5b44d09b 77779499 … (32 bytes) SHA-256("doSlim") = 51ad5f29 40210e3d … (unrelated)

What hashes are for: checking that two things are equal without keeping the thing itself. doSlim stores the SHA-256 of an invite token (T20), not the token, so a stolen database gives no working invites. A fingerprint of a key (lesson 2) is a hash of it. You cannot "decrypt" a hash; you can only guess inputs and compare, which is why a hash of something short, like a PIN, is weak.

7. From a password to a key

People remember passwords, not 32 random bytes. A key derivation function turns a password into a key. For passwords it must be slow on purpose, because a password is guessable and the attacker will try millions.

  • Argon2id (libsodium crypto_pwhash, used by T17) takes time and a lot of memory per guess, e.g. 64 MB and half a second. Memory makes graphics cards and custom chips far less useful to an attacker.
  • A random salt (16 bytes, stored in the open) is mixed in, so two accounts with the same password get different keys, and an attacker cannot precompute a table once for everyone.
  • The result is only as strong as the password. A 4-digit PIN has 10,000 values; at half a second each that is under 2 hours on one machine, minutes on many. That is why the pupil's key goes on the card (lesson 3) and the PIN only guards one iPad.

8. Three kinds of "encrypted"

Companies say "your data is encrypted" and mean very different things. The question is always: who holds the key?

KindProtects againstWho holds the keyServer reads the data?
In transit (TLS, the padlock)Wi-Fi snoopers, the networkYour browser and the server, per connectionyes
At rest (disk, database dump)A stolen disk or backupThe server (doSlim family spaces: DOQUIZ_DATA_KEY, D24)yes
End to endAll of the above, plus the server's ownerOnly the users' devices (doSlim classes and schools, D22)no

End to end means the device encrypts before upload and decrypts after download, and no key that opens the data ever reaches the server. Lesson 2 shows how two devices share a key when the server must not see it.
